# MC模组测试系统（智能动态版）

本Skill提供一套完整的模组测试流程，支持**运行前自动更新配置**，确保测试目标始终与最新代码同步。

## 核心特点

- **运行前询问**：每次执行测试前询问是否更新配置文件
- **自动扫描**：智能扫描模组代码结构，自动发现新增/删除的文件
- **增量更新**：保留现有配置，只更新变化的部分
- **模组无关**：不硬编码模组路径，支持任何 NeoForge 模组

### 流程说明

| 步骤 | 执行条件 | 输出 |
|------|----------|------|
| 0. 启动确认 | 每次触发测试 | 询问用户是否更新配置 |
| 1. 配置更新 | 用户选择"是" | 更新 `mod_structure.json` + 生成 `MODULE_ARCHITECTURE.md` |
| 2. 代码检查 | 无论是否更新配置 | 静态代码分析报告 |
| 3. 报告生成 | 测试完成后 | 测试报告 |
| 4. UI测试 | 测试模块包含UI元素时自动触发 | UI截图 + UI测试报告 |

### 关键规则

- **只有选择更新配置时**：才会生成 `MODULE_ARCHITECTURE.md` 文档
- **不更新配置时**：直接跳过步骤1，使用现有配置继续测试
- **架构文档位置**：`.trae/skills/mc-mod-test/config/MODULE_ARCHITECTURE.md`
- **UI测试自动触发**：当测试模块的 `ui_elements` 配置非空时，自动执行UI测试

### 版本号更新规则

配置文件中的 `version` 字段采用语义化版本号 `X.Y.Z`：

| 版本位 | 含义 | 递增时机 |
|--------|------|----------|
| **X** (主版本) | 模组架构发生重大变化 | 新增/删除整个系统模块 |
| **Y** (次版本) | 系统内有较大变化 | 新增/删除整个模块内的多个文件 |
| **Z** (修订版本) | 小幅调整 | 文件内容更新、文件重命名等 |

**版本号递增逻辑**：

| 变化类型 | 版本递增 | 示例 |
|----------|----------|------|
| 新增整个系统 | X + 1 | 1.0.0 → 2.0.0 |
| 删除整个系统 | X + 1 | 1.0.0 → 2.0.0 |
| 新增多个文件到某系统 | Y + 1 | 1.0.0 → 1.1.0 |
| 删除多个文件从某系统 | Y + 1 | 1.0.0 → 1.1.0 |
| 单个文件变化 | Z + 1 | 1.0.0 → 1.0.1 |
| 仅更新时间戳 | 不递增 | - |

**注意**：版本号只反映配置的实质性变化，不反映文件内容的微小调整。

## 第二步：代码静态检查

### 检查流程

1. **加载配置文件** → 获取测试目标列表
2. **遍历每个系统** → 检查是否启用
3. **检查文件存在性** → 验证配置中的文件是否存在
4. **检查方法存在性** → 验证配置中的方法是否存在
5. **API兼容性检查** → 检查已弃用的API调用

### 检查内容

#### 1. 文件结构检查

根据配置文件中的 `test_targets.systems` 列表检查：

```java
// 构建完整路径
String basePath = projectStructure.javaSource + "/" + projectStructure.mainPackage.replace(".", "/");

// 检查每个系统
for (system : testTargets.systems) {
    if (system.enabled) {
        String systemPath = basePath + "/" + system.package.replace(".", "/");

        for (file : system.files) {
            String fullPath = systemPath + "/" + file;
            // 检查文件是否存在
        }
    }
}
```

#### 2. 方法存在性检查

对于配置了 `test_methods` 的系统，检查方法是否存在：

| 系统 | 检查方法 |
|------|----------|
| 负重系统 | getTotalWeight, getMaxWeight, getSpeedPenalty, getHungerMultiplier |
| 其他系统 | 根据配置动态检查 |

#### 3. API兼容性检查

检查配置文件中列出的已弃用API：

| 旧API | 新API | 说明 |
|-------|-------|------|
| `AttributeModifier.Operation.ADDITION` | `ADD_VALUE` | NeoForge 1.21+变更 |
| `AttributeModifier.Operation.MULTIPLY_TOTAL` | `ADD_MULTIPLIED_TOTAL` | NeoForge 1.21+变更 |
| `event.setCanceled(true)` | 新事件处理方式 | 事件API变更 |

## 使用说明

### 触发方式

只需说：
- "模测"
- "模测测试一下"
- "测试一下"
- "运行测试"
- "测试新功能"
- "检查代码bug"
- "验证构建"

### 执行流程

**方式一：先更新配置再测试（含架构文档）**
```
你：模测
我：在执行测试之前，是否需要我先扫描并更新模组配置文件？
你：是的，更新一下
我：好的，正在扫描模组结构...
    [扫描结果]
    ✅ 配置已更新
    📄 正在生成模组架构文档...
    📄 MODULE_ARCHITECTURE.md 已生成
    现在开始执行测试...
    [继续测试流程]
```

**方式二：直接测试（使用现有配置）**
```
你：模测
我：在执行测试之前，是否需要我先扫描并更新模组配置文件？
你：不用，直接测试
我：好的，使用现有配置开始测试...
    [继续测试流程]
```

**方式三：强制刷新配置**
```
你：模测，并更新配置
我：好的，先更新配置再测试...
    [执行配置更新 + 生成架构文档]
    [继续测试流程]
```

### 架构文档说明

当选择 **更新配置** 时，会自动生成 `MODULE_ARCHITECTURE.md` 文档：

| 文档内容 | 说明 |
|----------|------|
| 总模块数 | 模组中所有配置的系统数量 |
| 已启用测试 | `enabled: true` 的系统，🟢 绿色标记 |
| 已禁用测试 | `enabled: false` 的系统，🔴 红色标记 |
| 文件清单 | 所有文件的完整列表和路径 |

**文档位置**: `.trae/skills/mc-mod-test/config/MODULE_ARCHITECTURE.md`

**查看文档**: 可以在任何时候打开查看，了解当前模组的测试覆盖情况

### 手动触发配置更新

如果想单独更新配置（不执行测试），可以说：
- "更新测试配置"
- "扫描模组结构"
- "刷新配置"

这些命令同样会：
1. 扫描模组最新结构
2. 更新 `mod_structure.json`
3. 生成 `MODULE_ARCHITECTURE.md` 文档

## 注意事项

### 配置文件格式

- 配置文件必须是有效的 JSON 格式
- `enabled` 字段决定是否测试该系统
- 路径使用 `/` 作为分隔符（跨平台兼容）
- 包名使用 `.` 作为分隔符

### 扫描限制

- 只扫描 `src/main/java` 目录下的 `.java` 文件
- 配置文件目录 `.trae` 会被忽略
- 测试报告目录会被跳过

### 命令兼容性

- Windows 使用 `.\gradlew.bat`
- Linux/macOS 使用 `./gradlew`
- 确保 Gradle 版本兼容

## 一、核心设计理念

### 1.1 要解决的问题

当前成长 =「刷怪 → 随机品阶饰品 → 固定 10 字段随机词条」，一条属性无法脱离装备流通。玩家无法：

- 定向积累某条属性（暴击、穿透…），只能反复刷
- 把低品阶装备的价值通过拆解/分解回流到可交易资源
- 按自己的 Build 组装一件装备
- 为未来的武器/护甲预留同一套自定义装备管线

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **一条属性 = 一个组件** | 组件是独立物品：掉落、交易、安装、拆解/分解返还的完整闭环 |
| **装备 = 白板 + 组件** | 装备本体只有基础属性与槽位，数值全部来自组件 |
| **数值掉落即锁定** | 普通组件掉落即掷出数值；仅「随机组件」安装时随机 |
| **安装耗精华** | 安装消耗部位精华 1 个；无绑定概念（bound 字段已删除） |
| **拆卸 = 整件概率损毁** | 拆卸成功则组件 100% 完整返回；失败则整件损毁。成功率 = 100% − 5% × 强化次数（强化 10 次 → 最低 50%） |
| **分解两路线** | 分解时可选「保留组件」（每组件 50% 返还）或「不保留组件」（无组件、材料加量） |
| **强化作用于组件本体** | 强化程度存在组件上；强化上限 10 次 |
| **旧档强制迁移** | 测试档可重开，P1 即含迁移工具 |
| **JSON 管数值** | 属性区间、档位、掉率、返还率全进 JSON，Java 只写逻辑与回退 |
| **渐进接入** | 先让组件能掉、能装、能生效，再改造重铸/强化/打造，最后铺白板武器护甲 |

### 1.3 一图流

```
怪物/宝箱 ── 掉落 ──────────────────────────────────────┐
                                                       ▼
属性组件(掉落锁定数值) / 随机组件(无值)                   
   │                                                   │
   │ 安装(耗部位精华 ×1)                                │
   ▼                                                   ▼
装备(白板 + 组件槽) ── 强化(组件本体, 至多10次) ── 重铸
   │                        │
   │ 拆卸(成功率 100%-5%×强化,  失败=整件损毁)
   │ 成功→组件完整返回
   ├─ 分解[保留组件] → 每组件 50% 返还 + 基础材料
   └─ 分解[不保留组件] → 无组件 + 额外品阶碎片(供强化)
```

## 二、属性定义体系

### 2.1 定义结构（数据驱动）

`attributes.json`：

```json
{
  "attribute_defs": {
    "max_health": {
      "category": "defense",
      "unit": "flat",
      "display": "最大生命值",
      "tiers": { "1": [1, 3], "2": [3, 5], "3": [5, 7], "4": [7, 10], "5": [10, 13], "6": [13, 17], "7": [17, 30] },
      "max_cap": 999,
      "applicable": ["accessory", "armor"]
    },
    "crit_chance": {
      "category": "combat",
      "unit": "percent",
      "display": "暴击率",
      "tiers": { "1": [0.005, 0.015], "2": [0.015, 0.025], "3": [0.025, 0.04], "4": [0.04, 0.06], "5": [0.06, 0.08], "6": [0.08, 0.12], "7": [0.12, 0.2] },
      "max_cap": 0.95,
      "applicable": ["accessory", "weapon"]
    },
    "_random_pool": {
      "_comment": "随机组件安装时的抽取池（属性表与权重由作者后续设计，先保留结构）",
      "pool": [],
      "tier_weights": { "1": 40, "2": 25, "3": 15, "4": 10, "5": 5, "6": 3, "7": 2 }
    }
  }
}
```

> V1.3 品阶适配：组件档位 T1~T5 扩为 **T1~T7**，与饰品 7 品阶一一对应（T1=残破 … T7=至臻）；区间锚点对齐 `attribute_essence_ranges.json` 品阶标准区间（`FINE_QUALITY_TIER_PLAN_V1.md` §二-D5）。

### 2.2 字段说明

| 字段 | 含义 | 备注 |
|------|------|------|
| `category` | defense / offense / combat / element / mage / special | 决定生效接入点与安装兼容表 |
| `unit` | flat（数值） / percent（百分比，存小数） / per_second（每秒） | 沿用 `AccessoryAttributes` 存储约定 |
| `tiers` | 档位 → [min, max]，1~7 档（对应 7 品阶） | 4 个用途：数值区间锚点 / 掉落分级 / 色阶与价值 / 装备品质门槛（§4.3） |
| `max_cap` | 全槽叠加后的绝对上限 | 衔接 `CritSystem` 95% / `DamageReductionSystem` 80% 钳制 |
| `applicable` | 可安装的装备大类 | 白板/武器/护甲的安装校验依据 |
| `_random_pool` | 随机组件的抽取池 | §3.2；属性与权重**待作者设计** |

### 2.3 属性分类清单（V1）

| 类别 | V1 实装属性 | 生效接入点 |
|------|------------|-----------|
| 基础 defense | `max_health` / `armor` / `damage_reduction` | Aggregate → AttributeModifier |
| 基础 offense | `attack_damage` / `movement_speed` / `luck` / `health_regen` | Aggregate → AttributeModifier |
| 战斗 combat | `crit_chance` / `crit_damage` / `armor_penetration` | `CritSystem` / `ArmorPenetrationSystem` |
| 元素 element（预留） | `fire_damage`…（按 `ElementType`） | `ElementSystem.getElementDamageBonus`（待系统完成） |
| 法师 mage（预留） | `intelligence` / `spirit` / `mana` / `elemental_affinity` | `MageAttributeSystem`（待系统实现） |
| 特殊 special（预留） | 套装件标记 / 技能组件 | `SetSystem` / 未来技能体系 |

> V1 只实装基础 + 战斗两类；元素/法师先支持「存储 + 掉落 + 安装」，生效钩子待对应系统完成后接上（§13.7 / §13.8）。

## 三、属性组件物品

### 3.1 物品设计

- 统一基类 `AttributeComponentItem extends Item`，DataComponent `ATTRIBUTE_COMPONENT` 存：

```java
record AttributeComponentData(
    String attributeId,   // 可为 null 或 "random" → 随机组件
    int tier,
    Double value,         // null = 未掷值（随机组件安装时才掷）
    int enhanceLevel      // 组件本体强化程度（§9），0~10
) {}
```

- 注册：`attribute_component_<attributeId>`（如 `attribute_component_max_health`）；
- 随机组件：`attribute_component_random`，无 `attributeId`/`value`；
- 颜色：按 `AttributeDef.category` + tier 映射（复用 `AccessoryDropRarity` 色系，T1 灰 → T7 红）；
- Tooltip：属性名 + 档位 + 数值 + 「随机属性（安装时确定）」/ 强化次数；
- **贴图：复用 `attribute_essence_*` 原贴图；随机组件无图 → 不做占位图**。

### 3.2 数值掷出时机（已定）

| 组件类型 | 掉落 | 安装 |
|---------|------|------|
| 普通组件（C1） | **掉落即锁定数值**（存 `value`） | 不再掷值 |
| 随机组件（C2） | 无数值（`value = null`） | 从 `_random_pool` 抽属性 → 抽档位（≤ 装备自身档位基准 + 1）→ 掷值 |

## 四、装备组件容器与白板装备

### 4.1 容器 DataComponent

```java
record InstalledComponent(
    String attributeId,
    int tier,
    double value,
    int enhanceLevel    // 组件本体强化程度 0~10
) {}

record ComponentContainer(List<InstalledComponent> installed, int maxSlots) {}
```

### 4.2 白板装备基类

`BlankGearItem extends Item`（未来武器/护甲可复用），携带：

- 基础属性（`blank_gear.json` 按部位定义，如白板戒指基础 2 生命）
- **品阶（已定：掉落/合成时即携带，槽位随品阶确定，打造不改变品阶）**
- 空组件槽（不携带容器或容器 `installed=[]`）

| 白板部位 | 基础属性示例 | 槽位来源 |
|---------|-------------|---------|
| 白板戒指 | 生命 +2 | 品阶定槽数（掉落/合成即定） |
| 白板项链 | 生命 +3 | 品阶定槽数（掉落/合成即定） |
| 白板武器（P5） | 攻击 +5 | 品阶定槽数（掉落/合成即定） |

### 4.3 槽位数与组件档位门槛（按品阶，初值）

**新增规则（已定）：对应品质的装备，只允许安装「比自身高一阶」及以下的组件档位** —— 例：精良（EXCELLENT）品阶的装备可安装史诗（EPIC，即第五档）及以下档位的组件。

> ✅ **已定稿（V1.3，随品阶改版同步）**：品阶已由 6 级扩展为 **7 级**——在「普通」与「精良」之间插入 **优秀（FINE）**（FINE=优秀，原 EXCELLENT 中文名改「精良」，见 `FINE_QUALITY_TIER_PLAN_V1.md`）；组件档位同步扩展为 **T1~T7**，与品阶一一对应（本表即 7 级正式表）。

| 品阶 | maxSlots | 自身档位基准 | 可安装组件档位上限（基准 + 1） |
|------|----------|------------|------------------------------|
| BROKEN 残破 | 1 | T1 | T2（普通级） |
| NORMAL 普通 | 2 | T2 | T3（优秀级） |
| FINE 优秀 | 3 | T3 | T4（精良级） |
| EXCELLENT 精良 | 4 | T4 | **T5（史诗级）** |
| EPIC 史诗 | 5 | T5 | T6（传说级） |
| LEGENDARY 传说 | 6 | T6 | T6（封顶） |
| MYTHIC 至臻 | 7 | T7 | T7（封顶） |

> 规则：已装组件 tier ≤ 装备「自身档位基准 + 1」；数值滚动区间仍取组件自身 `tiers` 档位（组件 T5 = 史诗级数值区间）。7 级下至臻可装至臻级组件（T7 封顶），解决传/至臻顶部断档。

### 4.4 安装兼容校验（§6 安装时执行）

1. 槽位未满；
2. `attributeId` 在装备适用集内（`blank_gear.json` 的 `allowed_attributes` 或按 `category` 白名单；随机组件安装前先抽属性再校验）；
3. **同属性不可重复安装（已定）**；
4. 组件 tier ≤ 装备自身档位基准 + 1（§4.3，如优秀 FINE 品阶装备 ≤ T4）；
5. 校验通过 → 组件写入 `COMPONENT_CONTAINER`。

## 六、安装与拆卸

### 6.1 安装（锻造台「打造/安装」页签）

**消耗：1 组件 + 1 白板装备（已有品阶）+ 部位精华 ×1**（已定）：

| 装备大类 | 消耗精华 |
|---------|---------|
| 饰品 | `accessory_essence` ×1 |
| 武器（P5） | `weapon_essence` ×1 |
| 护甲（P5） | `armor_essence` ×1 |

产出：组件写入 `COMPONENT_CONTAINER`。白板品阶在掉落/合成时即携带，安装校验直接基于白板品阶（§4.3）。

### 6.2 拆卸（已定：整件概率损毁制）

> 拆卸不做任何数值削弱；拆下后组件 **100% 完整返回**（属性/档位/数值/强化度全保留），只是**有概率整件损毁**。

| 项 | 规则 |
|----|------|
| 拆卸成功率 | **100% − 5% × 组件强化次数**；强化 0 次 = 100%，强化上限 10 次 = **最低 50%** |
| 成功 | 返回完整组件（含全部数值与强化度），可再次交易/安装 |
| 失败 | 组件整件损毁（不返还任何东西） |
| 消耗 | 部位精华 ×1（同安装） |

由此玩家需在「保住强化组件」与「承担损毁风险」之间权衡——强化越高的组件越难拆，防止无损倒腾。

## 七、分解返还

改造 `ForgeSystem.smash`。分解装备时**玩家二选一**（已定）：

### 7.1 分解模式 A：保留组件

| 产出 | 规则 |
|------|------|
| 组件 | **每个已装组件独立判定 50% 返还**；返还的组件完整保留数值与强化度 |
| 材料 | 基础产出：品阶碎片 50% / 属性精华按份额 25%（维持现有规则） |

### 7.2 分解模式 B：不保留组件

| 产出 | 规则 |
|------|------|
| 组件 | 全部不返还 |
| 材料 | **产出更多品阶碎片（对应装备品阶），用于强化组件**；具体加量：基础量 ×倍率（倍率待定） |

### 7.3 两条路线对比（设计意图）

| 路线 | 产出 | 适合 |
|------|------|------|
| 保留组件 | 组件 50%/个 + 基础材料 | 想回收已有组件 |
| 不保留组件 | 无组件 + 更多强化用碎片 | 装备已废、专心攒强化材料 |

> 数据入口：`smash_options.json`（50%、加量倍率等均配置化）；UI 分解页加单选开关，Payload 加 `keepComponents` 布尔。

### 7.4 校验

`ComponentSalvageSystem.salvage(stack, keepComponents)` 返回 `returns`（物品 id → count），沿用 `ForgeResult.returns` 路径，由 `ForgeOperationC2SPayload` 的 smash 分支统一发放。

## 八、重铸（改造）

现有 `reroll` 重滚 `AccessoryAttributes` 字段 → 改为操作**组件槽**：

| 操作 | 现有 | 组件化后 |
|------|------|---------|
| 普通重锻（`reroll_stone`） | 重滚基础词条、保留维度与强化层 | 随机重掷 1 个已装组件的数值（同属性同档位；保留 enhanceLevel） |
| 高级重锻（`reroll_stone_advanced`） | 重滚基础+强化，偏高 | 重掷全部组件数值且**偏高档**（复用 `advancedBiasShift` 逻辑） |
| 锁定石（`reroll_stone_lock`） | 锁定词条 | 锁定指定组件槽不参与重掷（最多 2 槽） |
| 白板装（无组件） | 不可重锻 | 不可重锻（提示无组件可滚） |

> 普通重锻不改变属性与档位、只动数值，避免「滚属性」击穿设计主题；换属性走「拆卸/替换安装」。

## 九、强化（改造）

### 9.1 目标（已定）

**强化作用于组件本体**：强化程度写入 `InstalledComponent.enhanceLevel` 与组件物品的 `ATTRIBUTE_COMPONENT.enhanceLevel`，**上限 10 次**。

### 9.2 方式

- 方向池 = 「已安装组件集合」（替代现有 `activeDirections(base)`）；
- 每次成功强化：随机选一个已装组件，`enhanceLevel + 1`，同时提升其数值（按档位上浮）；
- 消耗沿用 `FORGE_ENHANCEMENT` 的加价表（品阶碎片 + 成功概率），`bonus` 层逐步迁移进组件 `enhanceLevel/value`。

### 9.3 与拆卸的联动（已定）

拆卸**不削减**组件数值与强化度（完整返回），但强化次数越高拆卸成功率越低：

`拆卸成功率 = 100% − 5% × enhanceLevel`（enhanceLevel=10 → 50%）。

### 9.4 属性精华并入（已定）

属性精华功能并入组件体系：`attribute_essence_*` 不再「添加新属性」，改为**组件升级材料**（配合强化使用），物品与贴图直接沿用、不再单独注册新物品。

## 十、打造流程（白板 → 成品）

### 10.1 步骤（锻造台「打造」页签）

1. 放入**白板框架**（掉落/合成时已携带品阶，品阶决定槽位数，打造不改变品阶）；
2. 放入 **1~N 个组件**填入空槽（N ≤ 槽位数；随机组件可直接放入，安装时掷值）；
3. 提交（消耗对应部位精华 ×1）→ 产出成品装备（基础属性 + 组件容器）。

> 注：品阶由白板携带，打造=「填槽成型」，不再通过品阶碎片改变品阶；品阶碎片的角色回归强化/分解材料。

### 10.2 校验

- 组件档位 ≤ 白板自身档位基准 + 1（§4.3）；
- 组件分类兼容装备 + 同属性不重复（§4.4）；
- 组件数量 ≤ 槽位数。

## 十一、旧档迁移与生效链路

### 11.1 强制迁移（已定）

测试档可重开，**不做透明兼容兜底**；测试存档也可直接删除，迁移仅保证可玩性：

- P1 提供迁移工具：启动时将 `ACCESSORY_ATTRIBUTES` / `FORGE_ENHANCEMENT` 存在的装备一次性转换为 `COMPONENT_CONTAINER`：
  - 旧基础词条（非 0 字段）→ 组件（数值与档位换算见下）；
  - 旧 `bonus` 层 → 折算进对应组件的 `enhanceLevel`/value。
- 迁移产物不强制钳制档位——档位按现有 `attributes.json` 区间映射即可（§11.3）；存档可删，不追求完美。
- 迁移完成后 `ACCESSORY_ATTRIBUTES` / `FORGE_ENHANCEMENT` 可从 DataComponent 注册中移除（或保留仅用于迁移判断）。

### 11.2 「value → tier」迁移映射是什么（问答）

> **问**：这是什么映射？
> **答**：老档装备没有「档位」概念，词条数值是直接随机的（如戒指上 `max_health = 5.2`）。迁移时要把这条旧数值转换成「组件」存储格式，组件必须带一个 tier（T1~T7），所以需要一个规则来回答「数值 5.2 属于哪一档」。
>
> 规则（下文 §11.3）：取「区间最高 ≥ 旧数值」的最小档位；跨多档则取最接近档。例：`max_health` 档位区间为 T1[1,3] / T2[3,5] / T3[5,7] / T4[7,10] / T5[10,13] / T6[13,17] / T7[17,30]，旧值 5.2 → 落在 T3（[5,7]）→ 迁移为 `attribute_component_max_health, tier=3, value=5.2`。
> 这层换算只影响迁移结果，不影响新掉落装备（新装备直接有档位）。

### 11.3 迁移换算规则

1. 旧数值 ≠ 0 的每个字段 → 1 个组件；
2. tier = 满足 `tierMin ≤ 旧值 ≤ tierMax` 的档位；数值超出 T7 上限 → 钳制为 T7 并取上限值；
3. 维护一份逐条映射日志（仅开发环境打印），供作者核对是否走档合理。

### 11.4 统一聚合 API

`ComponentEffectAggregator.aggregate(ItemStack) → AggregatedResult`：

- 读取 `COMPONENT_CONTAINER` → 基础属性 + 组件投影到 `AccessoryAttributes` 视图（供旧读取点调用）；
- 元素/法师等扩展属性另出 `extended` 视图，供新接入点消费。

### 11.5 改造所有读取点

| 读取点 | 现状 | 改法 |
|--------|------|------|
| 各部位 handler（`RingEffectsHandler` 等） | `AbstractAccessoryEffectHandler.getRolledAttributes` | 改调聚合 API |
| `CritSystem` / `ArmorPenetrationSystem` / `DamageReductionSystem` | 直接循环读词条 | 改调聚合 API |
| `AccessoryTooltipHelper.addRolledTooltip` | 读 `ACCESSORY_ATTRIBUTES` | 加组件列表渲染 |

### 11.6 缓存签名（关键 bug 防护）

`buildEquipmentSignature` 追加 `COMPONENT_CONTAINER` 的 hash，否则**换组件后缓存不失效、属性不刷新**。

### 11.7 上限钳制

组件叠加后仍走现有钳制（暴击 ≤95%、减伤 ≤80%）；组件首版数值按「全槽满配也不超上限」反推。
